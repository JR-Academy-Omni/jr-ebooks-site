01 / 认识 FDE

FDE：把技术带进客户的工作现场

Forward Deployed Engineer，常译为前沿部署工程师或前线部署工程师。

你要解决什么问题？

客户已经有模型或产品，但还需要有人理解业务、接通数据和系统、验证结果、推动使用。FDE 在这些环节中动手实现，也与客户一起决定做什么、做到什么程度。

常见岗位 通常更关注什么
软件工程师 产品功能、系统设计、工程质量与稳定性。
AI Engineer 模型驱动的应用、检索、工具调用、评估与成本。
解决方案工程师 / 架构师 技术可行性、方案设计与验证；部分岗位也承担生产交付。
FDE 客户场景中的问题定义、代码与集成、上线和使用反馈，并把共性问题反馈给产品团队。

例子：客户想做一个知识助手

先问员工怎样找政策、谁维护资料、哪些人能看，再决定是否采用检索增强生成（RAG）：先找出相关资料，再让模型依据资料回答。之后还要证明答案能支持实际工作，并交给有人维护的团队。

这些是工作重心，不是统一的职位标准。本书聚焦企业 AI 应用交付，读者需要已有代码、API 和基础部署经验。

怎样理解岗位前景

当企业需要连接旧系统、处理数据权限、衡量任务效果时，这类交付能力有用。标准化工具也会吸收部分配置工作，因此长期要积累工程判断、行业理解和协作能力。这是基于工作需求的分析；具体机会再看下一章的澳洲、美国和中国招聘样本。

01 / 职责拆解

一项需求，要经过哪些人和决定？

FDE 需要把工程工作和客户决策接起来，也要说清责任边界。

工作阶段 FDE 的动作 留下什么
需求不清 观察用户流程，核对假设与限制 需求记录、范围与验收人。
选方案 比较替代方案，说明代价与依赖 方案建议书、架构决定。
实现与验证 编写集成代码，调查失败 可运行原型、测试与失败记录。
上线与使用 组织发布、培训和交接 运行手册、试点反馈、产品建议。

谁做决定？

业务负责人批准规则、范围和收益口径；资料负责人确认内容与版本；IT 与安全负责人批准接入；项目负责人安排资源。FDE 提出方案、实现控制并报告风险，不能替这些角色默默签字。

看 JD 时，确认实际重心

有的岗位偏系统部署，有的偏 Agent 配置和工作流，有的要求承担客户架构与技术领导。面试时问清：是否负责生产代码、同时支持几个客户、怎样验收、谁决定追加需求。

本书练习：面对“我们需要一个 AI 助手”，先写出用户、资料负责人、批准人和三个待验证问题，再开始选模型。

03 / 技能准备

从已有经验出发，补齐交付短板

下面是学习建议。选择真实目标岗位后，再决定需要补到什么程度。

你的基础 可以迁移的优势 优先补齐
后端 / 全栈 接口、数据模型、业务系统开发。 需求发现、AI 评估、范围和客户验收。
前端 交互、用户体验、工作流界面。 服务端、身份权限、数据接入与发布。

先做一次小规模交付演练

选一个自己理解的流程，找使用者验证问题；实现一条最小链路；保留五种失败情形；找另一位工程师按文档运行。最后讲清楚为什么这样做、哪里还不能上线。这比堆满工具名更有助于展示能力。

职业发展可以怎样延伸？

喜欢系统深度，可继续做高级 FDE 或架构工作；喜欢行业问题，可发展行业解决方案；喜欢跨项目协作，可尝试交付负责人；喜欢提炼共性需求，也可以转向产品工程。这些是能力延伸方向，并非所有公司都有固定晋升路径。

接下来进入工程实战：第 4–6 章形成方案，第 7 章运行离线实验，第 8–11 章补评估、发布和交接。每读完一部分，留下能被别人检查的材料。
03 / 项目地图

跟着 Northstar，完成一轮交付练习

Northstar 是虚构企业；角色、预算和试点计划是教学设定。代码与实跑记录单独标明。

业务目标与第一版边界

计划让运营和财务员工查询现行政策，核对原文，并知道何时需要人工帮助。首期只读，不自动批准报销。未来试点设为 40 人；本地程序只使用 4 个测试身份和少量教学文档。

章节 你会得到的成果
4–5 · 需求与方案 填好的需求记录 D01、方案与预算 D02。
6–7 · 架构与实现 架构记录 D03、权限实验、实际调用本地模型的问答程序。
8–10 · 验证与试点 实跑报告、验收矩阵 D04、发布记录 D05、测量计划 D06。
11–12 · 交接与展示 变更单 D07、接手步骤 D08、作品集说明 D09。

先学会读这几个词

PoC 是验证想法是否可行的小原型；ACL 是谁可以访问哪些资料的规则；Agent 会按任务调用工具或决定下一步；评估（Eval）用一组问题检查实际行为。其余术语随用随讲，附录提供速查。

配套包中 templates/ 是空白模板，worked-example/ 是填好的教学示例，reports/ 是实际运行记录。教学计划中的客户审批、用户收益与生产上线均未发生。
04 / 客户调查

先观察工作，再整理需求

一次访谈的成果应该能改变方案，而不只是增加会议纪要。

找谁 问什么 记录什么
一线用户 最近一次查政策，从哪里开始？最后找了谁？ 操作步骤、等待时间、无法继续的原因
业务负责人 什么结果值得继续投入？哪些错误不可接受？ 业务目标、基线、验收负责人
资料负责人 现行版本在哪里？旧版如何撤回？ 资料目录、版本、更新与撤回责任
IT / 安全 身份从哪里来？接口和数据访问由谁批准？ 接入条件、环境、权限、审批依赖

具体问法

把“你们查资料是不是很慢”改成“请演示昨天那次差旅政策查询”。记录用户在搜索、阅读、询问同事、核对版本上分别用了多久。等待别人回复的时间，和用户实际操作的时间分开记。

事实与假设分栏

事实：资料负责人确认有两个现行目录。假设：目录里的所有文件都适合入库。待验证：嵌入的表格能否正确解析。每条待验证项必须有负责人和完成日期，不能在方案建议书（Proposal）中悄悄写成已经具备。

本页交付：需求调研摘要（Discovery Brief）。至少写清一个具体流程、一位最终用户、一位批准人和三个可能改变方案的未知项。
04 / 范围与基线

把“提高效率”写成可检查的目标

先测现在如何工作，再提出目标；不要用演示速度代替业务收益。

一份可执行的基线采集方案

教学建议：选择正常、复杂、无答案三类政策问题，邀请运营与财务用户完成代表性任务。记录任务类型、开始与结束时间、答案是否正确、是否求助、重做时间。测试样本尽量覆盖不同熟练度；保留原始记录，不只报平均值。

范围项 首期决定 批准条件
现行政策 纳入已批准目录 资料负责人确认版本和权限
历史档案 暂不纳入 访问获批、预算与测试更新后再讨论
自动审批 不纳入 未来独立评估业务权限和写入风险
两个部门 分批启用 各部门有负责人和验收记录

写一条能验收的需求

“运营用户询问差旅政策时，系统返回现行版本的依据和引用；找不到可用依据时不猜测，提示联系负责人。”把“回答准确”拆为事实支持、版本正确、权限正确和下一步清楚，才能知道问题出在哪。

本章成果 · D01 需求记录

打开 worked-example/01-discovery.txt。已写出运营与财务的不同权限、三条本地需求，以及仍待客户验证的耗时和资料责任。练习时把其中一个假设换成你观察到的事实。

05 / 方案选择

不是每个问题都需要 Agent

先用最小的方案验证业务价值，再为确有必要的能力增加复杂度。

路线 适用前提 本案例判断
整理目录与传统搜索 主要问题是资料混乱或版本不可辨 必须先做，可作为比较基线
现成企业 AI 工具 现有权限、数据与功能条件满足需求 先验证接入与治理约束，再决定是否采购
定制 RAG 工作流 回答需要企业文档、引用与权限控制 首期候选：流程可预测、以只读为主
自主 Agent 任务路径变化大，需要动态选择工具 首期不需要；若扩展动作再单独评估

用相同问题比较候选方案

让相同身份在相同文档版本下完成相同任务。比较质量、总处理时间、维护工作、权限实现和完整成本。某个模型在通用榜单上的表现，不能替代你的业务验收。

一条架构决定记录

决定：首期只读 RAG。理由：主要任务是查找现行政策，不需要修改业务系统。替代方案：先改进目录检索。重新评估条件：用户确实需要跨系统执行动作，且动作权限与责任已明确。

Anthropic 的公开文章区分预定义工作流与动态 Agent，并建议从简单方案起步。本页选型表是针对教学案例的应用。
参考：S3 Anthropic｜Building effective agents。
05 / Proposal 与预算

让客户批准一个具体范围

方案要让业务、IT 和预算负责人都知道自己批准了什么。

Northstar 首期 Proposal 摘要｜教学设定

目标：验证政策查询是否能降低查找与核对负担。范围：两个部门、已批准的现行资料、只读问答与引用。交付：原型、权限与评估记录、受控试点、运行手册。依赖：身份接入、资料批准、业务专家参与。接口延期时先完成离线验证，不承诺按原计划上线。

06 / 系统架构

让权限成为数据路径的一部分

先确认谁能看什么，再决定把哪些内容交给模型。

已验证的用户会话
  → 服务端解析租户、用户、组与权限版本
  → 检索前限制允许访问的现行文档
  → 排序与选择证据
  → 生成带引用的草稿（或无依据转人工）
  → 检查引用范围与答案支持程度
  → 返回结果，并记录最少必要的运行信息

三条需要画在架构图上的边界

身份服务负责证明用户是谁；检索服务负责限制能取出的内容；模型只处理已经允许进入上下文的资料。不要把前端传来的 department 当成可信权限，也不要指望提示词替代访问控制。

引用链接也要验证权限

回答显示“见文档第 3 页”并不意味着文档可公开下载。打开原文件时仍应校验用户身份和权限。日志、缓存、错误信息与历史会话同样可能泄露内容，必须纳入设计。

本页交付：画出数据流，并在每条跨系统连线上写明身份来源、传输内容、授权方式与失败行为。微软公开样例的 ACL 文档可作为深入阅读。

06 / 数据与工具

接入之前，先约定失败时怎么做

接口契约既要定义成功结果，也要定义重试、撤回和不确定状态。

字段 / 约束 用途
document_id / version / status 识别资料、区分现行与已撤回版本
tenant_id / allowed_groups 限定可访问范围；缺失授权信息时默认不进入检索
owner / source_url / updated_at 追溯负责人、原文与更新状态
request_id / timeout / error_code 定位一次调用，区分超时、无权限与服务故障

MCP 与工具调用放在哪里

MCP 是连接模型应用与外部工具的一种协议。它和工具调用可以帮助接通系统，业务权限仍需自行设计。工具入口仍需校验当前身份、允许的参数和操作范围。首期提供只读查询；将来的写入能力，应具备审批、审计和重复执行保护。

写操作超时，不要盲目再执行

例如创建采购申请后响应超时，服务器可能已经成功创建。先用幂等键（标记同一业务操作，避免重复执行）或业务标识查询状态，再决定重试。只有重复执行不会新增副作用的操作，才适合自动重试；重试次数与总时长都要有限制。

08 / 评估设计

把“看起来不错”拆成可判定的问题

不同的错误需要不同的测试；一个总分解释不了所有风险。

维度 测试方法 教学验收示例
访问边界 跨部门、跨租户、撤权、缺失 ACL 关键检查全部通过；出现泄露立即停止
答案依据 逐条核对事实与引用是否对应 业务负责人按约定量表评分
版本 旧版撤回后再问相同问题 只使用现行资料；冲突转人工
拒答与转人工 无资料、模糊问题、证据冲突 返回正确状态与后续路径
成本与延迟 记录每次调用及复核工作 在项目约定预算和体验范围内

测试集要与开发材料分开

开发集用于改提示词和调检索；验收集由业务方确认并保留。看到验收失败后反复调到通过，相当于把它变成开发集，需要新增独立样本。对重复运行不稳定的任务做多次试验，不只展示最好的一次。

黄金答案未必是一句话

可以记录必须包含的事实、禁止出现的内容、允许的引用、预期工具状态和应转人工的条件。用代码检查权限与结构，用业务专家判断内容是否支持实际工作；模型评分也要抽检。

发布的是一组版本，不只是代码

建立发布清单

10 / 成本与效果

先算每次成功任务，再谈节省

模型账单只是成本的一部分，人工复核与维护也需要计入。

模型成本 = 输入量 × 输入单价 + 输出量 × 输出单价
月运行成本 = 模型 + 检索/存储 + 监控 + 维护 + 复核
每次成功任务成本 = 当期总成本 ÷ 成功完成的任务数
净释放工时 = 基线操作工时 - 新流程操作工时 - 新增复核工时

一个可复算的教学例子

假设每月 1,200 次查询，平均每次少用 3 分钟：释放 60 小时。若每次另需 1 分钟复核，净释放 40 小时。按 A$50 / h 的内部估值计算，产能价值为 A$2,000。若月运行成本假设为 A$900，价值扣运行成本为 A$1,100；这不是实际现金利润。

什么情况下不能说省钱

工资没有减少、工时没有转向有价值工作，就不能把所有释放时间写成现金节省。还需考虑一次性实施成本、试点样本偏差、返工和未被覆盖的任务。真实采购时，用当前供应商报价替换教学假设。

不要用一个快速成功请求代表全部体验。记录中位数、较慢请求表现、错误率与人工升级率，按任务类别比较。预算模板提供公式和待填字段。
10 / 用户采用

让试点回答三个业务问题

用户会不会用、能不能完成任务、值得不值得继续投入。

要回答的问题 采集方式 避免的误读
用户为什么不用 观察真实工作、访谈未使用者 登录人数不能解释使用障碍
是否帮助完成任务 记录完成率、复核时间与改写量 生成一段文字不等于任务完成
是否值得扩大 结合成本、质量、维护与反馈 次数增长不等于业务价值增长

培训围绕具体工作

让运营用户完成一次差旅查询：查看引用、核对版本、识别没有依据的结果、提交反馈。让财务用户体验权限边界和人工升级。培训时直接展示已知限制，不用一串顺利问答代替操作训练。

试点结论允许“暂缓”

如果使用者愿意用，但资料版本持续混乱，先修资料治理；如果效果仅在少数任务成立，缩小范围；如果成本和返工抵消收益，提出停止或换路线。停止条件应在试点前约定，不能等结果不好才改口径。

材料 接手者需要完成的动作
系统与配置说明 找到服务、环境、权限入口与配置来源
资料更新流程 新增一份获批政策，撤回旧版并验证查询
评估与发布记录 运行验收检查，解释失败项并决定是否发布
Runbook 定位故障、暂停功能、恢复服务、核对权限
支持与责任表 知道谁负责资料、代码、费用、审批与事故沟通

交接演练｜研发人员暂时不操作

接手者按文档处理一次“旧政策仍被引用”的故障。观察他能否识别索引与缓存状态、找到当前资料负责人、恢复正确版本并留下记录。卡住的位置就是文档或工具需要补充的地方。

明确已知限制与剩余责任

列出未接入资料、尚未验证的高风险任务、依赖的外部服务、维护工作和支持时间。验收矩阵逐项关联最初承诺与实际证据；尚未通过的项目要明确处置，不能藏在代码注释里。

本章成果 · D07 / D08 变更与交接

示例文件分别写出缩小范围的建议和接手命令。把模型服务关掉再恢复，让另一位工程师按 D08 操作；记录实际卡住的位置后再确认交接完成。

12 / 复用与作品集

把项目经验留下来，下一次少重做

复用前先区分通用能力与客户特有规则。

适合复用 需要重新确认
连接器接口与错误处理 客户 API、限额、身份与允许操作
评估运行器与报告结构 客户问题、业务规则与验收阈值
发布清单与 Runbook 骨架 实际环境、责任人、恢复步骤
权限过滤测试模式 租户边界、部门关系、撤权机制

把现场问题反馈给产品

例如：多个客户都需要验证撤权是否传播到缓存。整理最小复现、预期行为、影响范围、现有绕行方式和共同需求，提出可配置的能力。避免把某个客户的特殊流程硬编码成所有客户的默认值。

作品集按证据组织

展示客户问题、你的职责、方案取舍、架构、关键实现、失败与修复、测试结果及未验证范围。模拟项目明确标注模拟；团队项目解释个人贡献。截图之外保留可运行材料，让别人能够复核。

一句可信的项目描述：“完成教学知识助手的权限过滤、本地模型接入与引用检查，保留离线测试和真实生成记录；尚未验证生产身份与真实用户收益。”
12 / 实践路线

用四轮练习形成一个完整项目

以下是自学练习安排，不承诺固定时间内达到某个岗位要求。

练习轮次 完成什么 自查问题
第 1 轮：定义问题 访谈模拟、流程图、试点范围、Proposal 为什么值得做？谁批准？哪些仍是假设？
第 2 轮：实现关键链路 运行权限实验，新增部门与测试 身份来自哪里？无权限和无依据如何处理？
第 3 轮：接近真实环境 运行 ai_app.py 与实际模型，再扩展一条企业接口 哪些已实测？费用如何记录？失败怎样恢复？
第 4 轮：评审与交接 演示、变更单、验收矩阵、交接演练 换个人能否运行？什么条件下应该停止？

工程评审的六个追问

为什么选这个范围？为什么需要这个架构？如何证明没有越权？模型或接口失败时会怎样？完整成本怎么算？你还没有验证什么？用材料回答，不用“应该没问题”结束讨论。

何时继续读官方培训

你能解释一个端到端项目后，再按缺口选 API、模型、评估、治理或推广课程。完成课程与通过业务验收是两件事；学习记录可以展示，实际效果必须来自项目证据。

附录 A / 术语速查

读到陌生词，先理解它在项目里做什么

用同一个知识助手场景解释，避免只记缩写。

术语 在本项目中的含义
RAG · 检索增强生成 先查获准资料，再让模型根据资料回答；检索不一定必须用向量库。
Agent · 智能体 根据任务调用工具或决定下一步；本书的首期问答采用固定流程。
PoC · 概念验证 小范围验证技术或业务假设，成功后还需要试点和验收。
ACL · 访问控制列表 说明谁能访问哪份资料，本例用租户与组来表达。
Eval · 评估 用约定的问题、预期与评分方法检查系统行为。
MCP · 模型上下文协议 连接模型应用与工具或资料服务的协议，不替代业务授权。
幂等 同一业务操作重复请求时，不产生重复扣款、重复申请等额外效果。
Runbook · 运行手册 让接手者知道怎样检查、暂停、恢复和升级处理。
Token 模型处理文本的计量单位，不能简单当成中文字数。
Super 澳洲招聘中常见的退休金缴款项目；核对是否在报价之外。
不要为了展示工具而增加流程。比如本项目不执行报销审批，就无需为了使用 Agent 而加入自动写入动作。
附录 B / 评审练习

先自己做决定，再看参考思路

以下没有唯一答案，但答案必须交代依据和代价。

情境一：资料负责人说历史档案下周才获批

参考思路：保留现行政策试点，移除历史档案承诺；重新说明覆盖率与验收范围。接口未批准前，不能用个人账号或导出文件绕过审批。补充记录：谁批准、何时重新评估、增加多少验证工作。

情境二：多数答案正确，但出现一次跨部门泄露

参考思路：暂停相关路径，按事件流程评估影响；检查检索、缓存、日志和历史消息，修复后做负例回归。平均正确率不能抵消权限失败。上线决定应依据事先约定的阻断条件。

情境三：大家说很好用，却没人能说清节省多少时间

参考思路：保留定性反馈，但不写收益结论。补采任务基线、实际操作与复核时间，检查样本差异。若测量成本高，可先缩小到一种高频任务；不能直接把好评数量换算成现金。

情境四：客户要自动批准报销

参考思路：将只读问答升级为写入业务系统，是独立范围变化。确认规则、金额权限、审批、幂等、撤销与审计；先提出人工确认版本，不能靠加一段提示词就上线。
